2. Cohesion: one reason to change

How much the parts of a class belong together. The test you have: one sentence, no "and".

Sharper: count the reasons you would open the file. Two unrelated reasons, two jobs.

Board: stores which piece is on which square. Why open it? Storage changes. One reason.

Why would you open Game.java?

  1. Turns or history change. M8: the game knows it is over. M10: undo becomes Command.
  2. Move generation changes. M5: king safety. M12: castling, en passant.

Nothing on one list touches the other. Two jobs.

The rules committee does not care how undo is implemented.

What does this method read from this?

public List<Move> legalMoves() {
    List<Move> moves = new ArrayList<>();
    for (Position from : board.positionsOf(sideToMove)) {
        moves.addAll(board.pieceAt(from).pseudoLegalMoves(board, from));
    }
    return moves;
}

board and sideToMove. And it only passes them on. Never history. Never flips the turn.

Compare play: reads all three fields, writes two, cannot exist without the game.

A method that only forwards its class's state is visiting, not living there. Its signature says where it lives: (Board, Color) → List<Move>.

Wait for "board and sideToMove". Then ask what it does with them. Do not say "feature envy" — week 7.

3. Coupling: who knows about whom

How much one part must know about another to work.

Measured by one question: if this changes, what breaks?

Your repo after M3. Arrow = import

                 Main
              /   |   \
             v    v    v
  view  ─►  model  ◄─  engine  ─►  factory
                 ▲                   |

  model  ─►  (nothing of yours)

Every arrow points toward model. None points back. No cycle.

You can read Board.java without opening another file of yours. That is not luck.

Aren't the pieces' moves "rules"? Why model?

A piece's geometry is a fact about the piece, like its colour. A knight moves in an L whatever else is on the board.

What a piece cannot know: anything about the rest of the board. Is my king attacked? Whose turn? Has that rook moved?

Facts about one piece: model. Facts about the whole position: engine.

If pushed: "Could you write Knight correctly on an infinite empty board?" Yes. "Could you write isInCheck?" No.

What the layers buy

  • Test Board without a Game; Game without a screen
  • Read one layer at a time
  • Week 11: a Swing window without opening a file in model or engine

Separation of concerns is the goal. Cohesion and coupling are how you check you reached it: each part cohesive, coupled in one direction.

5. The loop has to live somewhere

Session 6's three candidates, again.

  • Board? Board stores. A second sentence today; by M5, when king safety follows, the whole engine.
  • Piece? Needs every piece of a colour. No piece can see the others. attacks is the most one piece can say.
  • Leave it in Game? Works. Costs two reasons to change, and M5 and M12 land in the class that does undo.
  • A new class. MoveGenerator, in engine: turns a position and a colour into the moves that colour may play.

Its shape follows from its sentence

public final class MoveGenerator {

    private MoveGenerator() { }

    public static List<Move> legalMoves(Board board, Color color)
           static List<Move> pseudoLegalMoves(Board board, Color color)
}

Nothing to remember → nothing to construct → static, private constructor, final. A namespace for functions. Math is one. PieceFactory is one.

Look at the signature: no Game. The generator does not know a game exists. M5's tests build a board from FEN and ask.

"A class can be a namespace" — once. Some of the room thinks every class must be instantiated.

Why does one method have no modifier?

Session 5: "a member with no modifier is visible to its package and nowhere else. We will use that in M4."

Main.java: pseudoLegalMoves(Board,Color) is not public in MoveGenerator;
           cannot be accessed from outside package

Outside engine, "pseudo-legal" is not a concept anyone should build on. A view that listed them would offer moves M5 forbids. Game.legalMoves() is the door.

Coupling control at the package level: an arrow the compiler will not let you draw.

Show it live: type the call into Main, build, read the message, delete it. Thirty seconds.
