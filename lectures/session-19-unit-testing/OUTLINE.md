# Session 19 — Unit testing: designing the cases · outline (revision 2, Nov 17, as built)

**Wednesday November 18 (moved from Mon Nov 16) · 75 min · Objectives 7 and 8 · M7 was due Mon Nov 16 · M8 (perft harness) next**

Students have run JUnit tests since M0 and read them as the specification
since session 4. Session 18 had them add JUnit to a plain project and write
one regression test (`readsTwoDigitMinutes`). Nobody has taught them how to
choose the tests: which inputs to try, how many, and how to know a test is
worth keeping.

One idea: *a test suite is designed, not collected. Split the inputs into
groups that should behave alike, test one case from each group and both
sides of every boundary, and keep a test only if you have seen it fail.*

What students should be able to do after class, on any project:

1. Write a unit test in arrange–act–assert form, with a name that states
   the behaviour, testing one behaviour, independent of the other tests.
2. Design cases from a specification: equivalence partitions, boundary
   values, and the usual edge cases (zero, one, last, empty, null, invalid).
3. Use `assertThrows`, `@BeforeEach`, and `@ParameterizedTest` with
   `@CsvSource`.
4. Judge a test, including one an agent wrote: does it fail when the code
   is wrong? Is the expected value worked out independently of the code?
5. Explain where an expected value comes from when you can't work it out by
   hand (a test oracle), and why perft is one for a move generator.

## 1. Where we are (0–5 min)

- You've passed hundreds of tests; you've written one. Today: how to choose
  them.
- Session 18's four `Playlist` bugs, on one slide: the last song (`>` vs
  `>=`), a two-digit number, before the first call (null), a fraction lost
  to integer division. **Every one was an edge case.** A designed test
  suite would have found all four before `main` ran.

## 2. What a unit test is (5–13 min)

- `readsTwoDigitMinutes` again, labelled: arrange, act, assert.
- Four properties: one behaviour per test; the name says the behaviour;
  independent (any order, alone); fast.
- `assertEquals(expected, actual)`: the order matters for the failure
  message. Show the message both ways.
- **Watch it fail.** Session 18's habit, now a rule: a test you have never
  seen fail might not be testing anything.

## 3. Choosing cases: partitions and boundaries (13–33 min)

- **The spec, no code:** `Playlist.formatLength(int seconds)` returns
  `"m:ss"`; `750 → "12:30"`; negative throws
  `IllegalArgumentException`.
- **Chat / laptops exercise (5 min):** list the inputs you'd test, and
  the expected output for each.
- Collect answers, then sort them on a slide:
  - **Partitions:** seconds under a minute; whole minutes; minutes and
    seconds; two-digit minutes; negative.
  - **Boundaries:** `0`, `59`/`60`, `599`/`600`, `-1`.
  - **The case people miss:** a seconds value under 10 (`65 → "1:05"`,
    not `"1:5"`).
- **Live coding (part 1):** write the tests from the list, with
  `assertThrows` for `-1`. Then paste in an implementation (written for the
  exercise, labelled as such) and run: one test goes red, at a boundary.
  Fix it, run green.
- **The engine already does this.** Given tests from M2 and M4, by name
  only: "a knight in the centre reaches eight squares" / "in the corner
  reaches only two"; "an empty board has no moves"; "a side with no king is
  never in check". The authors partitioned the board the same way.

## 4. Less repetition: three JUnit tools (33–45 min)

- **Live coding (part 2):**
  - collapse the boundary tests into one `@ParameterizedTest` with
    `@CsvSource({"0, 0:00", "59, 0:59", "60, 1:00", ...})`; each row
    reported on its own;
  - `@BeforeEach` for a fresh `Playlist` with three songs, used by new
    tests of `next()` wrapping after the last song;
  - why fresh each time: a test that depends on another's leftovers passes
    alone and fails in the suite, or the reverse.
- These come with `junit-jupiter`, already in your `pom.xml` and in the
  `Playlist` project from Monday.

## 5. Your turn (45–57 min)

- **Laptops, 10 min:** write tests for `totalMinutes()` (bug 4, integer
  division): pick the partitions (empty playlist, one song, a total that
  isn't whole minutes), write them, break the method on purpose and watch
  at least one go red.
- Two or three students read out their cases; compare.

## 6. Is this test any good? (57–65 min)

- **Question slide:** three short tests for `formatLength`, each passing,
  each weak:
  - expected computed with the same formula as the code;
  - asserts only `assertNotNull(result)`;
  - two behaviours in one test, so the first failure hides the second.
- Which would still pass if `formatLength` were wrong?
- **The check for generated tests (M7 allowed them):** break the code on
  purpose; if no test fails, the tests don't cover it. Expected values must
  come from the spec, not from running the code.
- IntelliJ **Run with Coverage**: shows lines no test ran. It shows what
  isn't tested, not that what ran is right.

## 7. When you can't work out the answer: oracles and perft (65–72 min)

- For `formatLength` you computed every expected value by hand. For "how
  many legal positions after three moves from the start?" you can't.
- **An oracle** is an independent source of the right answer: a
  specification, a slower but obviously correct version, or published
  numbers.
- **Perft** counts the positions reachable in exactly *n* moves. Published
  counts from the start: 20, 400, 8,902, 197,281. A wrong count means a
  rules bug somewhere; splitting the count by first move narrows it down.
- M8 is a perft harness in JUnit; the handout follows. No code today.

## 8. Exit question (72–75 min)

> A method `parseRank(char c)` turns `'1'`…`'8'` into 0…7 and throws on
> anything else. List the inputs you'd test, grouped into partitions, and
> mark the boundaries.
