Week 4 · September 14 – 18

OO Design & the Piece Hierarchy

Monday: what a Board and a Piece are, and one reason to change. Wednesday: where a piece can go — and why the answer is a class hierarchy, not a switch.

Milestones due: M1 — Monday, September 21 · M2 — Monday, September 28, both 11:59 PM

📋Topics covered

🌞 🌙

Monday — OO design

  • One reason to change — the single-sentence test for what a class is responsible for.
  • Value vs. identity, revisited — why Piece is a class when Position was a record, and which requirement decides it.
  • class ≠ mutable — every field final; whose fact hasMoved really is.
  • Values vs. entities — the distinction exists, database models are built the other way, and how other languages express a value.
  • Putting the answer with the data — PieceType carries its own letter, so no switch appears in the engine.
  • Composition — a board has 64 squares; it is not 64 squares.
  • Designing the interface first — what callers need, not what the array offers.
  • One flip, one place — [file][rank], FEN in toString, and why drawing the board is a view's job.
  • Packages — model, view, factory, engine, and what each is allowed to know.

Wednesday — inheritance & polymorphism

  • Ask the object, don't ask what it is — the switch that every question multiplies, and its replacement.
  • Inheritance vocabulary — extends, super, abstract, protected, @Override.
  • Dynamic dispatch — the call site does not know; open for extension, closed for modification.
  • Base class, subclass, helper — sliders and steppers; why there is no SlidingPiece; what the queen teaches about DRY.
  • Override vs. overload; substitutability — the pawn's attacks.
  • Abstract class vs. interface — Piece vs. PieceGlyphs.
  • Move — a value that remembers what it captured.
  • The one switch that is allowed — PieceFactory: switch at the edges, polymorphism in the middle.

🚀Milestone M1 — the domain model

M1 — due Monday, September 21 at 11:59 PM. Three classes — PieceType, Piece, Board — written from empty files, plus two view classes you are given and do not edit. The merge brings tests, the view, and nothing else.

  1. Merge the milestone. git fetch upstream --tags then git merge m1 — the compile error in PieceGlyphs.java names your first class.
  2. Build in order. PieceType → Piece → Board → toString() → Main. Each step makes the next one's failures readable.
  3. Go green — all of it. ./mvnw test → Tests run: 24, Failures: 0, Errors: 0, Skipped: 0. Twenty-four means M0b's eleven still pass.
  4. Print a chessboard. Set up the starting position in Main and render it through TextBoardRenderer — the actual point of the milestone.
  5. Commit, then submit by tag. git add -A && git commit first — a tag only captures what is committed — then git tag submit-m1 && git push origin main --tags and verify the tag shows on GitHub.

Graded by reading, not just by tests: Board's array stays private, and no model class prints, enforces a rule, or decides legality. "Board stores which piece is on which square" — one sentence, no "and".

♞Milestone M2 — the Piece hierarchy

M2 — due Monday, September 28 at 11:59 PM. Piece becomes abstract; six subclasses answer pseudoLegalMoves; a Move record says what a move is. The merge brings seven scaffolds, two given factories, and ten tests — and the build fails seven times with the same message, because your Piece has nothing to override yet.

  1. Merge: git merge m2 — "method does not override or implement a method from a supertype" ×7 is the assignment.
  2. Refactor Piece into the abstract base (Monday Sep 21, live), point Main at BoardFactory.standard(): 34 tests run, 10 red.
  3. Build: Move → Knight, King → Rook, Bishop, Queen → Pawn.
  4. Go green: Tests run: 34, Failures: 0, Errors: 0, Skipped: 0.
  5. Commit, then submit by tag: git add -A && git commit, then git tag submit-m2 && git push origin main --tags.

Graded by reading: no switch or instanceof on piece type anywhere in model, and no intermediate SlidingPiece class. Pieces answer for themselves.
